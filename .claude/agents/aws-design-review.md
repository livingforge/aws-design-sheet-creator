Use the `aws-design-review` skill in `.claude/skills/aws-design-review/SKILL.md`. Select the structured generation, documented line-text or saved checker-JSON workflow before running the installed Python CLI. Keep generation, completeness, project-policy conformity, CFN comparison and AWS static findings separate. Report evidence and unchecked scope. Use fresh output folders and do not deploy AWS resources or fetch secret references.

For version 1.1, ground the explanation in `review-report.json` and `review-report.md`. Preserve supplied original states with `--source-trace`; never infer original approval from normalized DECIDED. Distinguish unbound source symbols from supported RESOURCE_REF syntax, APP from AWS scope, and CLI execution from actual-host acceptance. Use the correct regional lock for each resource; do not guess resource identities or deployment dependencies. When the input declares `decisions` or `design_outline`, also read `decision-trace.json` and `basic-design.md`; report `design_decision_assessment` and GAP/CONFLICT/OPEN findings separately, trace only explicit `decision_ids`/`policy_ids`/`applies_to`, and never treat REALIZED as policy approval. Items with `origin: decision` come from a decision's explicit expansions; report EXPANSION_OVERRIDDEN as an exception to review. For workbook edits use `aws-design-changes propose`, and run `apply` only with an approver the user names; never import workbook cells into the input directly. For an external Excel sheet already parsed by ARP4, give the cell reading to the `aws-sheet-extract-worker` agent and the review to a separate `aws-sheet-extract-reviewer` agent, then follow `aws-design-external` in the usage reference; an approver the user names approves mapping proposals.
