# AWS design review skill: usage

This skill contains an allowlisted Python runtime, separate Tokyo, Osaka and us-east-1 CloudFormation acquisition locks, profiles and rules; it carries no tests or examples. The release root holds fictional sample documents in `samples/aoba-learning-hub/` (Word files, read through ARP4) with a guide to trying them. Copy only this skill into the chosen host location: `.agents/skills` for Codex, `.claude/skills` for Claude Code, or `.github/skills` for Copilot. Keep the contents together and preserve unrelated host settings. Development history, full project dossiers and large evaluation outputs are excluded.

## Start here: the design workflow

For a design project, `aws-design flow init --workspace WS --environment ENV [--arp-root ROOT] [--policy-pack PACK] [--source-trace FILE] [--evaluate]` creates `flow.json` (`--overview` adds the system-overview agreement stage); `aws-design flow status --workspace WS [--markdown]` reports the stages (sources, overview, input, policy, generate, review) read from the workspace files and returns one next step. `aws-design flow run all --workspace WS` performs every step that needs no person until one does (`run scan|generate` run one step). `aws-design flow people --workspace WS [--approver NAME] [--architect NAME] [--adopter NAME] [--reviewer NAME]` registers the people the user names, and their names fill the next-step commands; the decision guard still asks before such a command runs. Generation passes the approved source set, the system overview, trace and latest review decisions, writes `runs/NNN` and records the hashes it depended on. Steps that need a person (source-set approval, policy-pack adoption, review verdicts) are returned as a command and the role it needs, never run. DONE means the files are in place, not approval. `aws-design flow inbox --workspace WS --output FRESH_DIR` gathers every decision the workspace waits for (source-set statuses with the proposal prefilled, overview agreement, policy-pack adoption, P1/P2 review rows) into `inbox.xlsx`, with candidates only where they have a deterministic basis (the only resource of the referenced type as `→ ID`, requirements naming a missing quality attribute, decisions a boundary flow could cite as `方針 ID`). `aws-design flow decide --workspace WS --workbook inbox.xlsx` validates every filled row first and records them with the person written in the row or registered for the role; a row without a person refuses the whole workbook. Chosen candidates write new copies of the input or overview and switch `flow.json` to them. The sections below describe each command.

### Draft and final modes

`flow.json` holds `mode`. `aws-design flow init` writes `"mode": "draft"` unless given `--mode final`; a flow.json without `mode` is final. In draft mode `run all` settles, under `agent:aws-design flow draft` and a draft mark, what the final mode asks people: it makes the source set from the proposal (`sources approve` is not run; UNDECIDED documents are settled by rule: POSSIBLY_REFERENCE and ARCHIVE_FOLDER to REFERENCE, NEWEST_IN_ARCHIVE_FOLDER and VERSION_UNORDERED to CURRENT, a citable document with an original or parse problem to EXCLUDED; `approval.draft` is true and settled entries are `decided: DRAFT`), applies the policy pack with no adopter (its declarations stay UNCONFIRMED), takes the overview as a single draft, triages pictures before one reading per document that draws the system (see the diagram ledger), lets the asks ledger go out after its check without the independent review and does not wait for answers, stops at gates only for a contracts or generation FAIL, and skips the review stage. It ends by writing `runs/NNN/draft-report.md` (document statuses and relevance, what the draft settled, the picture triage, the gates, the asks, how to finalize); `aws-design flow draft-report --workspace WS` prints it as the workspace stands and `status` returns `draft_ready`. `aws-design flow mode --workspace WS --set final|draft` switches; to final, a draft source set and a candidate policy input are moved to `*.draft.json`, so the approver and the adopter are asked, and the readings gain their second reading and review, the asks ledger its review and the review pack its verdicts. A final workspace holding a draft set reports the sources stage STALE and `run all` scans again.

### Next steps of four kinds

`status` reports the stages sources, overview, input, policy, generate, gates and review, and one `next` step: TODO with a command that `run all` performs itself; WAITING_FOR_AGENT with `agent` (`name`, `count` of independent runs and the `handoff` to give each); DELEGATED, a decision the approved delegation policy covers, which `run all` records under `agent:aws-design flow`; and WAITING_FOR_PERSON with the command, the role and `delegation_refused` (codes saying why the policy did not cover it, such as `NO_POLICY`, `POLICY_CHANGED_AFTER_APPROVAL`, `RULE_SUSPENDED`, `UNDECIDED <document>`, `FINDINGS GAP 3`, `DRAFTS_DISAGREE`, `NO_DELEGABLE_ROWS`). The status also reports `delegation` (`in_force`, `problem`, `policy_sha256`, `suspended`). An agent loops on `run all`, starts the agents it is asked for and stops at WAITING_FOR_PERSON.

### Contracts

`aws-design contract list` names every handover contract; `schema --kind K` prints its JSON Schema (all are also in `schemas/contracts/*.schema.json`); `validate FILE… [--kind K]` and `validate --workspace WS` check files with the models the commands use, including cross-references, and report error locations and types only, never values (exit 2 on failure). A file over its byte limit is `INPUT_TOO_LARGE` with its `size` and the `limit`, never mistaken for a syntax error (`NOT_JSON_OR_YAML`): handover files keep a 2,000,000-byte limit, and a diagram ledger, which lists every drawing of the documents, 64,000,000. Diagram ledgers and reviews are JSON read by the same loader the `aws-design diagram` commands and the flow use, so a file passes here exactly when they accept it. A file's contract is recognised from an explicit `contract` (`gate-report/1` …) or the version and keys each older format carries. In a workspace every JSON/YAML file in `flow.json`, `sources/`, `input/`, `reviews/`, `delegation/`, `delegation/log/`, `delegation/audits/`, `diagrams/` (with `diagrams/parts/*/` and the `adoptions/` folders; `retired/` readings are kept, not checked), `runs/*/gates.json` and `runs/*/agent-review/` must satisfy a contract; an unknown file there fails. `flow.json` itself is validated on every command (`CONTRACT_INVALID`). The design input's schema depends on the regional catalog: `aws-design document --schema input --schema-version 1.1`.

### Gates

Each `run generate` writes `runs/NNN/gates.json` (contract `gate-report/1`); `aws-design gate run --workspace WS [--run NNN] [--markdown]` evaluates them again. Gates: `contracts` (every workspace handover file), `source_set` (the approved set matches ARP4; the design cites no superseded or excluded document), `grounding`, `grounding_self_test`, `diagram_coverage` (see "Diagram ledger"), `service_mentions` (see below), `overview` (no CONFLICT) and `generation` (not exit 2). Grounding follows each decided literal setting (and each scalar leaf of a COMPOSITE) to its citation in the approved source set: `DOCUMENT_ID#s1-C5` (ranges `s1-C5:D9`, several separated by commas) names cells, `DOCUMENT_ID#s1-d4` a drawing (its text and alternative text), `DOCUMENT_ID#シート名` a sheet, `DOCUMENT_ID` the document; a value cited to a node or edge read from an image (`DOCUMENT_ID#v:VISUAL/n:NODE`) is INTERPRETED. Results: GROUNDED (the normalised text, number or boolean word is in the cited cells), TRACED (covered by the flow's `source_trace`), DECISION (linked by `decision_ids` and citing no source of its own: the value comes from the decision), INTERPRETED (the cited cells do not hold the value but the setting's `rationale` says how it was derived, such as a unit conversion; it does not fail and the review pack lists it for a person), FOUND_IN_DOCUMENT / NOT_FOUND_IN_DOCUMENT (only a sheet or document cited), NOT_CHECKABLE (not an ARP4 document of the set), and the failing NOT_FOUND (cited cells do not hold the value), CITES_NOT_CURRENT and UNSOURCED (a literal with no source on the setting or its resource). A link to a decision does not excuse a setting that cites cells from being checked against them. The self-test plants a value no document holds into one grounded setting and must see it fail. FAIL makes the gates stage WAITING_FOR_AGENT for `aws-design-review`, the skill's own session, to fix its input in a new copy; WARN continues. `aws-design gate ground DESIGN [--arp-root R --source-set S] [--source-trace T]` grounds one input outside a workspace. The `service_mentions` gate (contract `service-mentions/1`, written to `runs/NNN/service-mentions.json` and `.md`) reads every cell and drawing text of the CURRENT documents for AWS service names from a fixed dictionary (official names and usual abbreviations such as CloudTrail, KMS, SNS, Secrets Manager, ALB, mapped to CloudFormation types; abbreviations match in upper case only, and the longest name wins, so CloudWatch Logs is not also CloudWatch) and gives each named service one state: IN_DESIGN (a resource of a matching type, or an AWS_SERVICE actor whose service or name names it), CITED (a setting, override, resource, connection, actor, account or environment cites a cell or drawing that names it, as X-Ray tracing on a function does), NOTED (a requirement, operation, issue or decision cites such a cell, saying why it is not built) or NOT_IN_DESIGN, which fails the gate (code SERVICE_NOT_IN_DESIGN with up to three cell IDs). Only cell and drawing citations count, not a sheet or a whole document. Role words (監査ログ, 暗号鍵, 通知, 証明書) are listed as hints when none of their candidate services is in the input or named, and never fail. The report holds service names, document IDs and cell IDs only. SKIPPED without an approved source set or an input. A gate is a check of the handover, not of the AWS design.

### Delegation policy

`aws-design delegation init --output WS/delegation/policy.json [--preset standard|strict]` writes a draft; `show POLICY` prints what agents may decide and what stays with people; `approve POLICY --approver NAME --output WS/delegation/approval.json` records a person's approval bound to the policy's canonical sha256 (agent names are refused, and the decision guard asks first); `status --workspace WS` reports each rule as DELEGATED or the reason it is not. Rules (each omitted or `enabled: false` means not delegated): `source_set.accept_reasons` (proposal reasons accepted as proposed; UNDECIDED documents and source issues always go to a person); `overview.require_second_draft`, `require_distinct_models`, `allow_findings` (GAP, OPEN; CONFLICT never); `policy_pack.packs` (pack ID → optional sha256 pin); `review.reviewers` (2–5), `require_distinct_models`, `canaries` (planted rows per packet; P2 only, never P1); `external_mapping.require_distinct_models`; `audit.sample_rate`, `max_error_rate`, `min_audits`. Each agent decision writes `delegation/log/NNNN-<rule>.json` (contract `auto-decision/1`) and its record carries `delegation` (policy hash, rule, the agent actors it rests on, evidence hashes). Commands that record a person's decision (`aws-design sources approve`, `aws-design system approve`, `aws-design review-pack record`, `aws-design policy-pack apply --adopted-by`, `aws-design external approve`, `aws-design flow people/decide`) refuse `agent:` names. Changing the policy file voids it until a person approves it again.

### Agent review of P2 rows

With the review rule delegated, `run all` writes `runs/NNN/agent-review/packet.json` (contract `review-packet/1`): the P2 rows not escalated before, under opaque keys, mixed with canary rows whose value was changed to contradict their evidence; the key stays in `delegation/keys/` and is not given to agents (the guard refuses reading it). The flow then asks for `aws-design-checker` runs in the role `review-pack-checker`, each writing `verdicts-<actor>.json` (contract `agent-verdicts/1`). When enough verdict files exist, `run all` voids any reviewer who passed a canary, skipped a row or (if required) shares a model, records OK only for rows every remaining reviewer passed into `reviews/decisions-NNN-agents.json`, writes `escalation.json` (contract `agent-escalation/1`: AGREED, CANARY_MISSED or INSUFFICIENT_REVIEWERS, with every escalated row and the reviewers' reasons) and regenerates. Agents never record NG; doubted rows go to people, and escalated rows are not sent to agents again.

### External mapping agreement

`aws-design external agree --extraction … --structure … [--document …] --items FIRST --items SECOND --review REVIEW [--dictionary D] --workspace WS --output FRESH` approves, under the workspace policy's external_mapping rule, the proposals of FIRST that SECOND makes identically for the same value cell when none of the item's cells is among the cells `compare` finds in disagreement. REVIEW must accept FIRST and come from a third actor; both readings must pass `check`. Entries carry `approved_by: agent:A+agent:B` and `delegation`. Exit 3 lists the escalated proposals for `aws-design external approve` by a person.

### Golden set, audits and calibration

`aws-design golden score --manifest M --candidates DIR --candidate LABEL [--output FRESH]` compares candidate outputs (`DIR/<case id>.json`) with the expected answers of a `golden-manifest/1` (cases `external-items`, `system-overview`, `agent-verdicts`, each with `min_agreement`); exit 3 when a case fails or is missing. `aws-design delegation audit sample --workspace WS --output FRESH [--seed N]` writes `audit.xlsx` with the policy's share of agent decisions not yet audited; a person marks CORRECT/WRONG and `audit record --workspace WS --workbook audit.xlsx --auditor NAME` stores `delegation/audits/<id>.json` (the decision's target must be unchanged). `aws-design delegation calibrate --workspace WS [--golden REPORT …]` recomputes `delegation/calibration.json`: a rule is suspended when its audited error rate exceeds `max_error_rate` with at least `min_audits` audits, when a golden report fails for it, or (review) when two of the last three packets missed canaries. Suspension only narrows the approved policy.

## Install on Windows

Every `aws-design` command writes UTF-8 to standard output and error, whether its output is JSON or text. Windows PowerShell 5.1 decodes a command's output with the console code page, so run `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false); $OutputEncoding = [Console]::OutputEncoding` once in the session before capturing or piping it; otherwise Japanese document IDs come back garbled and are reported as unknown documents. Write reports with the commands' own `--output` rather than `>`, which re-encodes the text.

The locked release requires Python 3.12 or newer, excluding 3.14.1 because the pinned networkx dependency excludes that interpreter. Windows/Python 3.12.10 is the tested platform. From the skill directory:

```powershell
& .\scripts\install.ps1
```

The script creates a new `.venv` and installs the package from its local source, with tested dependency constraints from `requirements.lock` and the official PyPI index. Before that it lists earlier installations and asks before removing them: this copy's existing `.venv`, `aws-design-review` copies of an older version in the `.claude`, `.agents`, `.github` and legacy `.codex` skill folders of the same project and of the user profile, and `aws-design-sheet` installed into the Python used for installation. Copies of the same or a newer version, or without a readable version, are listed and kept. Confirmed folders go to the Windows Recycle Bin, together with their schema caches; the new copy downloads the current archives. The package is removed with `pip uninstall`, which the Recycle Bin cannot restore; an editable install keeps its source folder. Nothing changes when the answer is no, when a folder is not on a local drive with the Recycle Bin enabled, when it would not fit there, or when the selected Python lives inside a folder to remove. In a non-interactive session the script stops after the list; `-Force` removes the listed items without asking. For optional free-text extraction, `-Llm` installs Anthropic support; this sends input text to an external API, needs separate credentials and may incur charges. It was not exercised in this release. The default local workflows need no API/AWS credentials. The installer then runs `aws-design bootstrap --all-regions`: initial network access is required to download the two exact pinned archives from the public official AWS regional URLs and build the local catalog. No AWS login is needed. The ZIP and generated schema/catalog files are not distributed.

## Run a check

The default extractor accepts UTF-8 lines such as:

```text
VPC main: CidrBlock=10.0.0.0/16; EnableDnsSupport=false
Subnet private-a: Vpc=main; CidrBlock=10.0.1.0/24; AvailabilityZone=ap-northeast-1a
```

Formal CloudFormation resource type names can also be used. Run from the skill directory, replacing the paths and metadata with the user's inputs:

```powershell
& .\.venv\Scripts\aws-design.exe run INPUT.txt --project PROJECT --environment prod --account ACCOUNT_ID --intermediate .\output\design.json --result .\output\result.json
& .\.venv\Scripts\aws-design.exe excel .\output\result.json --design .\output\design.json --output .\output\report.xlsx
```

When working from a different directory, use absolute paths for the CLI executable, input, and output. Set `--region` explicitly for a different region and provide a matching schema snapshot. For saved intermediate JSON, use `aws-design check INPUT --output RESULT`. `status: COMPLETE` means the process finished; review individual verdicts and `coverage` for unresolved scope. Both commands export the design as CloudFormation templates and check them with cfn-lint, which the install script installs as a dependency; `--no-cfn-lint` skips it. The checker does not certify AWS deployability.

## Generate a design workbook (input v1)

The independent `aws-design document` command creates a workbook before CFN exists:

```powershell
& .\.venv\Scripts\aws-design.exe document INPUT.yaml --environment dev --output output/my-design
```

Add `--cfn TEMPLATE.yaml` to compare explicit CFN logical-ID bindings. Use a fresh output directory. Generate the input contract locally with `aws-design document --schema input --schema-version 1.0`; version 1.1 requires the installed schema cache. Output: `design.xlsx`, `design.json`, `summary.json`. `GENERATED` means document generation succeeded; `NOT_EVALUATED` remains the design evaluation status.

The supported documentation catalog covers VPC, Subnet, SecurityGroup, EC2 Instance, RDS DBSubnetGroup, DBInstance and DBCluster. Input IDs and references are validated. Common settings and whole-setting environment overrides remain separate. Undecided/not-applicable decisions, explicit defaults, external references, unresolved expressions and secret references are distinct. Never enter secret values: use SECRET classification plus SECRET_REF with a secret:// or ssm:// reference. Do not put secrets in prose or identifiers. References are not fetched.

The 12-sheet layout includes requirements, inventory, service settings, connections, operations/recovery, open issues, differences, environment overrides and provenance. Long text continues on additional rows with the same item ID; strings are not formulas. A3 landscape printing is configured. Editing arbitrary Excel cells cannot update the input. The normalized document contract is independent of the checker's Design JSON, and cannot be passed directly to `aws-design check`. CFN comparison does not evaluate deployability or network reachability.

## Review and verify check results

Corrections to saved checker data and rule maintenance are maintainer tools of the development checkout, not part of this package; a design check never changes the bundled rules.

## Schema-driven design documents (1.1)

Use `python -m aws_design_sheet.document_cli INPUT.json --environment ENV --output FRESH_DIRECTORY`. Optional `--cfn TEMPLATE.json` compares declarations. The index workbook links service volumes (`--volume-size 10`). Version 0.3.0 preserves the original 50 service groups and adds Cognito: At review, Tokyo had 51 groups / 608 resource types / 4058 writable top-level properties; us-east-1 had 51 / 640 / 4197. A later official archive can differ. These are generation inventories, not whole-service validation coverage. Secrets must be references. Export input contracts locally with `aws-design document --schema input --schema-version 1.1`; developer evaluation scripts are not bundled.

The installer runs `aws-design bootstrap --all-regions`. Locks cover ap-northeast-1 (Tokyo), ap-northeast-3 (Osaka) and us-east-1. Use `--check --all-regions` offline, or `--region ap-northeast-3` for one pinned region. Each archive, manifest, receipt and catalog stays in `schemas/.cache/<region>/<archive SHA-256>/<lock SHA-256>/`. Missing regional locks and corrupt or tampered caches fail explicitly, with no Tokyo fallback. Format-3 locks accept a newer official archive: setup prints `review_status` (REVIEWED_EXACT or DRIFTED_FROM_REVIEWED) and `review_drift` counts, the cache keeps `drift.json` with the added/changed/removed types, and the rule ledger is reconciled so changed types are review-required. Generation repeats the status in `summary.json` catalogs and adds a notice when drifted. Format-1/2 locks still stop on any archive change. Regional rule review status is retained separately; a Tokyo review is not approval in another region. A type keeps its Tokyo ledger state in another region only when `rules/schema-reviews.json` records a regional review of that region's exact type schema (SHA-256 of its canonical JSON); a schema-change record likewise covers one exact new type schema. Any other fingerprint, region or baseline re-opens the question. The Osaka lock carries 687 types recorded this way (schema identical to the reviewed Tokyo snapshot, no regional wording in their rules, references, checks or open questions); the others keep the regional question.

Each version 1.1 resource can set `region`; omission uses the selected environment region. Ordinary references must satisfy existing environment/account/region checks. Only CloudFront viewer certificates in ACM and explicitly CLOUDFRONT-scoped WAF in us-east-1 have narrow cross-region reference handling. Other account or physical-ID unknowns stay unresolved. A single `--cfn` comparison cannot represent a multi-region design and is rejected. Optional `accounts` declare the AWS accounts by stable ID (`id`, `name`, `purpose`: WORKLOAD, MANAGEMENT, SECURITY, LOG_ARCHIVE, NETWORK, SHARED_SERVICES, BACKUP or OTHER, `account_id` only when a document gives the 12 digits, `description`, `rationale`, `status`, `sources`); an environment's `account` places its resources unless a resource names its own `account`, and an AWS_SERVICE actor may name one too. A setting naming a resource in another declared account is reported for review with `--evaluate` (DOCUMENT_CROSS_ACCOUNT_REFERENCE, NEEDS_REVIEW), and a single `--cfn` comparison cannot span accounts. A resource's `environments` lists the environments it exists in (omitted: all of them); in any other environment it has no settings, no override, no connection and nothing present may reference it, and generation leaves it out of that environment's items, workbook, basic design and diagram (`design.json.absent_resources`). Environments may cite `sources`, such as the frame a diagram draws around one. Optional `actors` name what the system exchanges data with but the input does not model as a resource: `id`, `name`, `kind` (USER, OPERATOR, EXTERNAL_SYSTEM, or AWS_SERVICE for an AWS service outside the catalog, with `service` and optional `region`), `description`, `rationale`, `status` and `sources`. They hold no settings; a TRAFFIC connection may start or end at one, other kinds may not, and a service the catalog holds must be a resource. They appear in `basic-design.md`, the inventory sheet and the diagram. Explicit `connections` of kind `DEPENDENCY` are checked for graph cycles; this does not infer CloudFormation DependsOn, stack dependencies or deployment order.

## Source states and machine-readable explanation (1.1)

Every 1.1 generation writes `review-report.json`, `review-report.md`, and the same report inside `design.json` and workbook sheet `実行サマリ根拠`. Read these before writing a narrative. `summary.json.review_report_file` points to the report. Source states cannot be recovered from normalized DECIDED status or from rationale prose.

When explicit original states and bindings are available, add `--source-trace trace.json`. The trace is a JSON list (or an object with a `rows` list). Example row:

```json
{"setting_id":"SET-012","kind":"CFN","item_ids":["subnet.AvailabilityZoneId"],"source_pointer":"/settings/11","source_snapshot":{"setting_id":"SET-012","kind":"CFN","status":"EXTERNAL_INPUT_REQUIRED","verification_status":"NOT_RUN"}}
```

IDs must be unique and match the snapshot; status and verification_status must be explicit strings. Every item binding must exist. APP rows must have empty item_ids; an unmapped CFN row needs an explicit exclusion_reason. The full snapshot can preserve other source fields. The original input is not modified. Saved `source-trace.json` preserves these rows. `source_status_counts` and `source_verification_counts` report original states separately from `normalized_status_counts`. Without a trace they stay empty and trace.status is NOT_PROVIDED. Trace validation checks identity/state/bindings only; source fidelity requires independent audit.

The object form may also carry the source's own approval: `{"rows": [...], "document_approval": {"status": "APPROVED", "status_text": "承認済", "approvers": ["..."], "date": "2026/06/05", "status_cell": "book.xlsx#表紙!C13"}}`, and any row may carry `"item_review": {"status": "ACCEPTED", "text": "OK", "pointer": "book.xlsx#VPC!E5"}`. Document statuses are APPROVED, IN_REVIEW, DRAFT, REJECTED, UNRECOGNIZED, NOT_RECORDED, NOT_CITED and FORMULA_NOT_ADOPTED; item statuses are ACCEPTED, CHANGES_REQUESTED, NOT_REVIEWED, UNRECOGNIZED, NOT_RECORDED and FORMULA_NOT_ADOPTED; other fields are strings or string lists. `review-report.json.source_review` reports `document_approval` (NOT_CITED for a trace without it, NOT_PROVIDED without a trace), `item_review_counts` and `generated_items_by_item_review` (NOT_PROVIDED or MIXED where rows lack or disagree). These are transcriptions of the source, not approval by this tool, and a blank is never read as approved.

`review-report.json.rule_review_causes` splits RULE_REVIEW_REQUIRED coverage into REGIONAL_APPLICABILITY (a type not yet reviewed for this region), SCHEMA_CHANGE (the official schema changed since the review) and OPEN_QUESTION (an existing ledger question). `counts` counts coverage rows and `resources` the distinct resources per cause.

`RESOURCE_REF` is supported. The unresolved reason `SYMBOL_TARGET_NOT_BOUND` describes a symbol without an explicit resource-ID binding, not an input-format limitation. Physical IDs are not fetched. Report APP business scope, unregistered requirements, unchecked conditions and regional review questions separately. CLI completion cannot establish actual host invocation: `host_acceptance` remains NOT_VERIFIED_BY_CLI, and whole_design_approval remains NOT_ESTABLISHED. Original NOT_RUN states are preserved even after local static evaluation.

Input decision status and value resolution are separate: `EXPRESSION_MATCH` is only expression equality and never deployment approval. Office/PDF source extraction and PDF export are not part of this minimal distribution. Workbook generation uses openpyxl and does not require Microsoft Excel.

## Basic design decisions and traceability (1.1)

One 1.1 input can hold both the basic design (policy prose) and the parameter sheet (settings). Optional `decisions` declare policies: stable `id`, `section`, `title`, `statement`, `status`, `rationale`, `alternatives`, `requirement_ids`, `policy_ids` (existing `project_policies`), `sources` and optional `applies_to` (`resources` and/or `types`, optional `environments`). `section` must be in `design_outline` (a list of `{id,title,required}`); when omitted the standard outline is used: overview, non-functional, account, network, compute, data, edge, security, monitoring, backup-dr, operations. Any setting, including a COMPOSITE `$design` leaf or an environment override, may list `decision_ids`. Unknown or duplicate links are structure errors.

Every 1.1 generation writes `basic-design.md`: chapters in outline order, each decision with its realizing settings, a Mermaid diagram of declared connections and appendices. It also writes `architecture.drawio` (`summary.json.architecture_diagram_file`), a draw.io diagram of the environment with draw.io's built-in AWS icons: AWS Cloud, region, VPC and subnet frames, main resource types and the declared connections. A resource is placed in a VPC or subnet only through its own effective RESOURCE_REF settings (subnets, VPCs, security groups, subnet groups) or a VPC gateway attachment; nothing is placed from names, CIDRs, routes or defaults. A subnet frame is green (public) when a route table associated with it routes to an internet gateway, blue (private) when it has another route table, and grey when the input associates none. Resources neither of a main type nor in a connection are listed in full in the diagram's note; when such resources name two drawn ones (a listener its load balancer and certificate, a user pool domain its pool and certificate, a route table's associations and routes a subnet and a gateway or endpoint), a dashed line labelled `経由：` with their name joins those two. Actors stand outside the AWS Cloud frame, an AWS_SERVICE actor inside its region. The diagram shows declared placement only, not reachability or approval. Its layout is computed, the same for the same input: inside each frame, items joined by lines stand in left-to-right columns, lines turn at right angles between columns and never run through an icon, and resources without lines sit in rows below, grouped by icon colour and type; very tall columns fold and very long flows wrap into bands, and long names are shortened on the picture only. Subnets with a decided availability zone sit in a zone frame, and a resource spanning several subnets stays in the VPC with a dashed tag in each subnet it references. With declared accounts, each account is a frame inside AWS Cloud holding its regions and global services. The file's first page is the whole environment; with two or more accounts or regions it adds a page for each holding only the resources placed there (lines to the others left out), and a whole page for every other environment of the input, each drawn from that environment's own effective settings. Adjust the presentation in draw.io if wanted. When decisions or an outline are declared, `decision-trace.json` (also in `design.json` and sheets `設計方針`, `方針トレース`, `方針指摘`) reports per decision `realization` (REALIZED, PARTIAL, NOT_REALIZED, LINKED, DOCUMENT_ONLY, NO_TARGET_IN_SCOPE, NOT_IN_ENVIRONMENT, UNDECIDED, NOT_APPLICABLE) and `mechanization` (DESCRIBED, TRACED, CHECKED). Findings are GAP (SECTION_EMPTY, DECISION_NOT_REALIZED, NO_TARGET_IN_SCOPE, REQUIREMENT_WITHOUT_DECISION, SETTING_WITHOUT_BASIS), CONFLICT (DECISION_UNDECIDED_BUT_SETTING_DECIDED, DECISION_NOT_APPLICABLE_BUT_LINKED, LINK_OUTSIDE_DECISION_SCOPE) or OPEN (DECISION_UNDECIDED, REALIZING_SETTING_UNDECIDED). Read `summary.json.design_decision_assessment` separately from other statuses; it does not change the exit code.

Only declared links are traced. Decision prose is never interpreted, no setting value is derived from a decision, and REALIZED only means each in-scope resource has a decided setting citing the decision, not that the policy is satisfied. `SETTING_WITHOUT_BASIS` covers top-level explicit values with no decision, rationale or source; REFERENCE connections document their RESOURCE_REF properties. Edit the input and regenerate instead of editing `basic-design.md`.

A decision with `applies_to` may declare `expansions`: `{property, mode (LITERAL, RESOURCE_REF or EXTERNAL_REF), value or ref, classification (not SECRET), environments, types, rationale}`. Only DECIDED decisions expand, only into absent top-level settings of in-scope resources (optionally narrowed by `types`). Explicit common or environment settings always win; a different explicit value is the CONFLICT `EXPANSION_OVERRIDDEN`, an equal one is MATCHED_EXPLICIT. Expanded items have `origin: decision`, the expansion's input pointer and the decision ID, and feed the checklist, project policies and AWS evaluation like ordinary settings. Two expansions for one setting, unknown properties, sensitive properties and invalid references are structure errors. `decision-trace.json.expansions` and sheet `方針展開` list every result.

## Workbook proposals (1.1)

Service setting sheets of 1.1 workbooks have edit columns `修正案（値）`, `修正理由` and `適用先（共通/環境）`; sheet `概要` holds `@import-key` (input SHA-256 and environment). Reviewers type only into those columns. `aws-design changes propose INPUT GENERATED_DIR_OR_XLSX... --output proposal.json` reads them without modifying the input: a value is JSON when it parses, otherwise text; `未決定` makes the setting UNDECIDED; the reason is required; the target defaults to where the value came from. Formulas, dates, secret-like values, COMPOSITE/secret targets, several cells for one item, unchanged values and results that fail input validation are listed in `rejected` with a code. A workbook generated from a different input fails as STALE_WORKBOOK.

`aws-design changes apply INPUT proposal.json --output NEW_INPUT.json --approver NAME (--all | --change ID ...)` writes a new JSON input and appends `change_log` records (before, after, reason, approver, UTC time, proposal and workbook SHA-256). It refuses a changed input or target (STALE_PROPOSAL), an existing output and a missing approver. `--generate DIR` regenerates the proposal environment; read its decision trace and checklist with the change. Decisions, requirements and other prose are edited in the input, not imported from workbooks.

## External design sheets parsed by ARP4

`aws-design external` turns an external per-service Excel design sheet into a 1.1 input. It does not read Office files itself and ARP4 is not bundled: the sheet must already be parsed by ARP4 (`extraction.json`, `document.yml` and a structure view whose ARP review is accepted). Agents decide what each cell means and cite cells by ID only; the CLI checks every claim against the extraction and copies the values.

1. Worker (an `aws-design-author` run in the role `sheet-extract-worker`) reads `aws-design external schema --kind items` and `aws-design external view --extraction E --structure S --document D`, writes the items file and fixes it until `aws-design external check … --items ITEMS [--dictionary DICT]` reports PASS. Every non-empty cell, including hidden sheets, is a resource name or evidence, an item, an extension, an unmapped item or a reasoned exclusion.
2. Reviewer (an `aws-design-checker` run in the role `sheet-extract-reviewer`, a different actor) compares the claims with the cells and records `aws-design external review … --decision accepted --actor NAME --reason TEXT --output REVIEW`. The CLI refuses the worker's actor name and a failing check; `build` rejects a review of a different items file. Codex has no bundled agent definitions; run the two roles as separate sessions with distinct actor names.
3. Mapping proposals become dictionary entries only through `aws-design external approve … --approver NAME (--all | --item ID ...) --output NEW_DICT`, with an approver the user names. Never approve as the agent.
4. `aws-design external build … --dictionary DICT --review REVIEW --base BASE --source ORIGINAL.xlsx --output FRESH_DIR` writes `input.json`, `source-trace.json`, `external-mapping.json`, `external-coverage.json` and `external-trace.xlsx`. `base.json` holds `system` and `environments` (with regions); they are never inferred from the sheet. `--source` only hashes the original before and after and stops on a mismatch with the ARP record. Exit 0 is COMPLETE, 3 is INCOMPLETE (outputs written), 2 is an input or check error.
5. Generate as usual: `aws-design document out/input.json --environment ENV --output FRESH_DIR --source-trace out/source-trace.json`.

Mechanical part first: `aws-design external suggest … --dictionary DICT` lists value cells whose accepted ARP header is an approved dictionary label, with the label cell, the expected state and the candidate entries (no cell values, no resource choice; notes, unit and review columns are skipped). `check` reports `mapping_counts` (items on approved entries versus new proposals).

Optional cross-check: run two workers independently (different actor names, neither sees the other's file) and compare them with `aws-design external compare … --items A --items B [--dictionary DICT]`. Resources are matched by type and name cell and items by value cell, so their own IDs may differ. The report lists only cell IDs and the fields that disagree (kind, resource, paths, state, ref, conversion), never cell values; exit 0 is AGREE, 3 is DISAGREE. Send only the disagreeing cells to the reviewer and the person who decides. Agreement is not proof of correctness.

If the sheet has an approval block, the items file cites it as `approval` (`status_cell`, `approver_cells`, `date_cell`, `note_cells`); an item may cite its row's review column as `review_cell`. The CLI transcribes them with built-in words (承認済/承認/Approved, レビュー中, ドラフト, 差戻し …; OK/済/確認済, NG/要修正, 未/未確認 …) and the dictionary's user-approved `approval_words` and `review_words`. A blank is NOT_RECORDED, other words are UNRECOGNIZED with warning `APPROVAL_WORD_UNKNOWN` or `REVIEW_WORD_UNKNOWN`, and a review cell cannot be the value cell (`REVIEW_CELL_IS_VALUE`). `source-trace.json` carries `document_approval` and `item_review`, `external-coverage.json.source_review` counts them, and `import_status` does not depend on them.

States must match the cell: LITERAL, UNDECIDED / NOT_APPLICABLE / DEFAULT only for such words in the cell, BLANK for an empty value cell, FORMULA (never its cached result), RESOURCE_REF when the text equals another resource's name cell, SECRET_REF for `secret://` or `ssm://`, and SECRET_VALUE for a clear-text secret. BLANK, FORMULA and SECRET_VALUE are not written to the input; secret values are masked in every output. Missing relations such as a VPC or subnet group are `unmapped` with `NEEDS_CONFIRMATION` and a follow-up, not guesses. Paths are checked against the regional catalog, including required members of array elements (`INCOMPLETE_ELEMENT`). Error codes name cells, never values.

`import_status` is COMPLETE only with an accepted review, no unapproved proposals, no unwritten items and no unmapped items. It describes the conversion, not design approval. ARP4 does not extract data validations, defined names, protection or external links; `unchecked_scope` records them as NOT_EXTRACTED_BY_ARP. Secret values still reach ARP4's extraction and the worker's context, so replace secrets with references in the original before import. JSON outputs are byte-identical for the same extraction, structure, items, dictionary, base and schemas; the agents' readings can differ between runs. Nothing is written back to the original.

## System overview

Before design sheets, describe the system above AWS resources in a separate overview file (`aws-design system schema`): requirements, actors, boundaries (account, region, environment, network, trust), components (functions, data stores, interfaces, shared services, operations), data flows, quality targets (availability, RPO, RTO …) and open questions. It links down into a 1.1 input only through explicit IDs (`realized_by.resources`/`decisions`, flow and target `decision_ids`). `aws-design system check OVERVIEW [--design INPUT] --output DIR` writes `system-overview.md` (nested-boundary diagram, gaps, components, targets, requirement trace, open items) and `system-overview-check.json`. GAP codes: REQUIREMENT_NOT_PLACED, COMPONENT_WITHOUT_REQUIREMENT/BOUNDARY/FLOW, QUALITY_TARGET_MISSING, BOUNDARY_FLOW_WITHOUT_DECISION and, with a design input, COMPONENT_NOT_REALIZED, QUALITY_TARGET_WITHOUT_DECISION, REQUIREMENT_NOT_IN_DESIGN, RESOURCE_NOT_IN_OVERVIEW. CONFLICT: REQUIREMENT_FROM_OLD_DOCUMENT, UNKNOWN_DESIGN_REFERENCE, REQUIREMENT_TEXT_DIFFERS. OPEN: ITEM_UNDECIDED, OPEN_QUESTION, REQUIREMENT_NOT_APPROVED_IN_ARP. `aws-design system approve OVERVIEW --approver NAME --output FILE` records agreement by a person the user names (refused while conflicts remain). Links are never inferred and the check is not approval. `aws-design system diagram OVERVIEW --output FRESH` writes `system-overview.draft.drawio`, a draft picture to look at before the design input exists: boundaries nested as frames, components inside them, actors and the data flows (dashed while undecided). The picture and the file say DRAFT with the overview's SHA-256 and its open items (undecided components, flows and quality targets, unanswered questions); it is never `architecture.drawio`, which each generation draws from the design input, and nothing reads it back.

`aws-design system init --arp-root ROOT [--source-set SET] [--category C ...] --system-id ID --name NAME --output FILE` starts an overview from the ARP4 registry (requirement records by default, retired ones left out; IDs lower-cased). Each requirement keeps its ARP ID, category, module, approval and evidence documents, and `arp.basis` judges the evidence against the source set: CURRENT, REFERENCE_ONLY, OLD_DOCUMENT (superseded, excluded or a different extraction revision; a CONFLICT), NOT_IN_SOURCE_SET, NO_EVIDENCE or NOT_CHECKED. `sync OVERVIEW … --output NEW` refreshes them, keeping kinds and statuses people set and reporting changed, retired (kept as NOT_APPLICABLE) and added requirements. `design-requirements OVERVIEW --input INPUT --output NEW_INPUT` adds the decided requirements to a copy of a 1.1 input without overwriting existing ones (differences are reported), reusing or adding sources whose locator is the document ID.

Drafting: an `aws-design-author` run in the role `overview-drafter` writes the overview from `init` and the CURRENT documents with `author` set and every element citing requirements (ELEMENT_WITHOUT_REQUIREMENT otherwise); an `aws-design-checker` run in the role `overview-reviewer` records `aws-design system review OVERVIEW --decision accepted|rejected --actor NAME --reason TEXT --output FILE` (the author's name and drafts with conflicts are refused); `aws-design system compare A B` lists where two independent drafts place requirements differently, plus differing targets, boundaries and actors (exit 0 AGREE, 3 DISAGREE). `aws-design flow` requires an accepted review of a drafted overview before asking people to agree it. Codex has no bundled agent definitions; run the roles as separate sessions with distinct actor names.

`aws-design document … --system-overview OVERVIEW` checks the overview against the input being generated, writes `system-overview.md` and `system-overview-check.json`, and adds the assessment to `summary.json`; an unreadable overview stops generation (SYSTEM_OVERVIEW_INVALID). Review-pack rows then carry the `components` that realize their resource and those components' `requirements`, and overview GAP and CONFLICT findings join P1. `aws-design flow` passes the overview automatically.

## Diagram ledger: what the documents draw (1.1)

Architecture diagrams in the CURRENT documents are read element by element before the input is written, so that nothing they draw is lost or folded together. ARP4 extracts each drawing (shape, picture, connector, group, graphic) with its text, alternative text, anchor, group and recorded connector ends, keeps images as assets, and its accepted structure may hold per visual a graph read from an image (`reading.method: vision`, with image evidence such as a region drawn by `arp4 spec structure render`). This package reads ARP4's files; it does not read Office files or images itself.

- References: `s1-d4` (the fourth drawing of sheet or slide 1), `a3` (the third image asset no drawing shows), `v:VISUAL/n:NODE` and `v:VISUAL/e:2` (a node and the second edge of an accepted visual's graph).
- `aws-design diagram view --arp-root R --source-set S [--document D]` lists every element of the CURRENT documents with its kind, texts, place (`at=` cells; a group member's place within its group), the groups and frames around it, a line's course (`runs=`), recorded ends, the drawings near an end the original does not record (`near=`, a guess), arrowheads, a picture's image file and each visual's image evidence with its path; its first line explains the keys. `schema --kind ledger|review` prints the contracts (`diagram-ledger/1`, `diagram-review/1`).
- Ledgers are kept per document: `diagrams/parts/<NAME>/` (NAME is the document ID made safe for a folder, with a hash) holds `ledger.json` (the reading the design uses), `reading-2.json` (the independent one), `review-<sha12>.json`, `adoptions/` and `retired/`. A workspace that already holds `diagrams/ledger.json` or `reading-2.json` keeps that single ledger for every document. A part ledger lists its own document only (`check --for-document D`; another document fails DOCUMENT_NOT_IN_PART), so reading one document again touches neither the other parts nor their reviews. The coverage reads all parts together: a document whose part has no ledger fails DIAGRAM_NOT_LEDGERED and each part's missing, stale or rejected review fails with that part's documents.
- A ledger (written by an `aws-design-author` run in the role `diagram-extract-worker`) gives every element of each document exactly one disposition: RESOURCE (with `service`), ACTOR (with `actor_kind`), BOUNDARY (`boundary` ACCOUNT, ENVIRONMENT, REGION or AZ with `value`, VPC, SUBNET, ON_PREMISES, OTHER), CONNECTION (optional `ends`, `line`, `legend`), ANNOTATION, LEGEND, DUPLICATE (`duplicate_of`, `reason`), OUT_OF_SCOPE (`reason`), UNRESOLVED (`reason`, `ask`), EXPANDED (a picture whose content its visual's graph holds) or GROUP (a group drawing that only bundles drawings with their own dispositions; a line ending on it ends at what it holds). It binds each document's extraction hash and, when anything relies on a visual, the accepted ARP4 review's content hash; per document it states `contains_architecture` with a reason. A document that draws nothing of the system (screenshots, operation screens, notes) may instead be set aside as a whole with `scope: NOT_ARCHITECTURE`, `contains_architecture: false`, a reason and no elements: its elements count as out of scope, the input may not cite them (CITES_OUT_OF_SCOPE_DOCUMENT), and the check warns NOT_ARCHITECTURE_HAS_SIGNS with the lines joining two drawings, the drawings naming AWS or network things and the graphs it holds, for the review to weigh. `preflight` gives these `architecture_signs` per document beforehand as a suggestion only. Element text is never copied.
- Draft mode: `run all` writes `diagrams/triage.json` (contract `diagram-triage`; `aws-design diagram triage --workspace WS` writes it too) for the approved set. Per CURRENT document with drawings it holds the architecture signs, the document's kind, each picture with its SHA-256, format and size, and why it needs no look (HAS_TEXT, READ_IN_ARP4, NO_FILE, SMALL below 160 px on its longer side or 20,000 pixels in area, or 20,000 bytes without a size, DUPLICATE of an image met earlier); the rest are handed to an `aws-design-author` in the role `diagram-triager`, which records each with `aws-design diagram look --workspace WS --image SHA --kind ARCHITECTURE|NETWORK|SCREENSHOT|TABLE|PHOTO|LOGO|OTHER|UNVIEWABLE [--service NAME]... [--note TEXT] --actor A` (services only for ARCHITECTURE and NETWORK; formats a viewer does not open take only UNVIEWABLE). Looks are kept by image hash when the triage is built again. A document is ARCHITECTURE when its drawings name AWS or network things, hold a graph, its kind is ARCHITECTURE or one of its pictures was seen as ARCHITECTURE or NETWORK; PENDING while a picture of it waits; NOT_ARCHITECTURE otherwise. ARCHITECTURE documents with drawings other than unread pictures get one `diagram-extract-worker` reading each; the draft coverage joins those readings with the input as the final coverage does, with REVIEW_MISSING and REVIEW_STALE as warnings, counts set-aside documents as out of scope, warns TRIAGE_PENDING, and checks the services architecture pictures show against the input (WARN PICTURE_SERVICE_NOT_IN_DESIGN, PICTURE_SERVICE_UNKNOWN); a missing or stale triage fails (TRIAGE_MISSING, TRIAGE_STALE).
- `aws-design diagram preflight --arp-root R --source-set S [--ledger L]` tells, before any worker reads, what each CURRENT document with drawings will need: element counts by kind, the structure review state, pictures without text or alternative text and those of them no accepted graph reads (WARN PICTURE_WITHOUT_GRAPH: open them first, and read the ones that draw the system in ARP4 before the workers start), lines whose ends the original does not record (WARN LINE_ENDS_WITHOUT_EVIDENCE when no rendered image can settle them), STRUCTURE_NOT_ACCEPTED, and the estimated ledger size: FAIL DOCUMENT_OVER_LIMIT (exit 2) when one document's ledger would pass the 64,000,000-byte limit, WARN SINGLE_LEDGER_OVER_LIMIT when all of them together would, which matters only to a workspace that keeps a single ledger. With an existing ledger it also says per document whether its entry is CURRENT, LEDGER_STALE, STRUCTURE_STALE (with the `expected` and `recorded` structure hashes) or NOT_LEDGERED. It reads only ARP4's files, so workspaces sharing an ARP4 root and source set get the same answer.
- `aws-design diagram check … --ledger L [--design INPUT] [--workspace WS]` checks the ledger against the drawings (exit 2 on FAIL), and with an input the coverage below. `compare --ledger A --ledger B` lists the elements two independent readings disagree on (exit 3), each with the `fields` that differ, its classes (MISSING, RESOURCE, PLACEMENT, CONNECTION, ACTOR, NOTATION; `code` is the first) and a `severity`: MAJOR when it changes what an element is, where it sits, what a line joins or whether it is there, MINOR when only how a drawing that maps to nothing is filed differs; the report counts them `by_class` and gives each document's agreement rate. Equivalent service names (`AWS::Lambda::Function`, `Lambda`, `AWS Lambda`) are one service. `check`, `compare` and `preflight` print a summary by default: counts by code and by document and the first `--limit` (20) rows, failures and MAJOR first; `--offset`, `--document` and `--code` page and filter them, `--full` prints every row, and `--output FILE` (a new file) keeps the full report while the summary names it. `--progress` (or `AWS_DESIGN_PROGRESS=jsonl` for every command, including `flow status` and the gates) writes one JSON line per document read or checked to standard error: `progress` (read, check), `done`, `of`, `document`, `elapsed_s` and `eta_s`. Work is kept per part, so after an interruption the flow resumes at the parts not yet read or reviewed. `review … --ledger L --decision accepted|rejected --actor NAME --reason TEXT --output diagrams/review-<sha12>.json` records an `aws-design-checker` review in the role `diagram-extract-reviewer`; it refuses the author's name and a failing check.
- The input maps elements by citing them in an object's own `sources` (`DOCUMENT_ID#s1-d4`): a resource or an AWS_SERVICE actor for a RESOURCE, an actor for an ACTOR, a connection for a CONNECTION, an account, environment, VPC or subnet for those boundaries. REGION and AZ boundaries are values, ON_PREMISES and OTHER need no target.
- Coverage (`aws-design diagram coverage --workspace WS --output FRESH`, and the gate `diagram_coverage`, which writes `runs/NNN/diagram-coverage.json` and `.md`). FAIL: DIAGRAM_NOT_LEDGERED, LEDGER_NOT_CURRENT, LEDGER_STALE, ELEMENT_UNCLASSIFIED, UNKNOWN_ELEMENT, ELEMENT_LISTED_TWICE, STRUCTURE_NOT_ACCEPTED, STRUCTURE_STALE, VISION_WITHOUT_EVIDENCE, EXPANDED_WITHOUT_GRAPH, GROUP_NOT_A_GROUP, PICTURE_NOT_READ (a mapped picture with no text read by parser), CONNECTION_ENDS_UNKNOWN, TARGET_MISSING, KIND_MISMATCH, CITES_UNMAPPED_ELEMENT, AGGREGATED_ELEMENTS and AGGREGATED_SERVICES (several elements the diagram draws apart cited by one object), PLACEMENT_MISMATCH and PLACEMENT_NOT_DECLARED (the account, environment, region, zone, VPC or subnet frames around an icon disagree with the input or the input declares none), CONNECTION_ENDS_MISMATCH, NO_CONTRIBUTION, ARCHITECTURE_FLAG_CONTRADICTED, UNRESOLVED_ANSWERED (an answered ask not carried into the ledger), REVIEW_MISSING, REVIEW_STALE, REVIEW_REJECTED. WARN: SERVICE_MISMATCH, PLACEMENT_UNVERIFIED (the input has no network reference to confirm a VPC, subnet or zone), DIRECTION_DIFFERS, LINE_END_UNMAPPED, GRAPH_NOT_EXPANDED, and for UNRESOLVED elements ASK_NOT_DRAFTED, UNRESOLVED_PENDING or UNRESOLVED_HELD (a person chose to hold it). The report gives Source elements, Mapped resources, actors, boundaries and connections, Legends and annotations, Duplicates, Groups, Expanded images, Out of scope, Unresolved, Coverage and Result, and separately the input's AWS service types, logical resources and placements (a resource in each environment it exists in) by account, environment, region and zone. Coverage counts elements with a target or an explicit disposition; 100 % does not mean every element became a resource.
- In the flow, the `diagrams` stage comes before `input`: for every part without readings two independent readings are handed off at once (`count` 2 per part with a `runs` entry each, naming its `document`: `ledger.json`, and `reading-2.json` by another actor that never reads the first), then the review of each first reading (several reviews are one handoff with `runs`). The stage tells how many parts are reviewed and is DONE when all are.
- `aws-design diagram adopt --workspace WS [--document D] --actor NAME --reason TEXT` makes a part's independent reading the one the design uses when it passes its check; the former `ledger.json` moves to `retired/<sha12>-ledger.json`, and the flow then asks for a new independent reading. `retire … --reading ledger|reading-2` moves a reading to `retired/` so its replacement is written to a fresh file. Each writes an `adoptions/*.json` record (contract `diagram-adoption/1`: action, the adopted and retired hashes and authors, where the retired file went, who decided and why). `--document` names the part in a workspace of parts and is left out in one with a single ledger. Pictures without text are read in ARP4 before the readings, so both read the same accepted structure: the first handoff carries the `preflight` command and says how many pictures without text, alternative text or graph to open first. A contract error in a ledger names the rule it breaks. A ledger failing with LEDGER_STALE, STRUCTURE_STALE or LEDGER_NOT_CURRENT goes back to its worker with `stale_documents` and what to re-read (STRUCTURE_STALE means the ledger is behind a structure ARP4 accepted again, not that the structure needs another review); STRUCTURE_NOT_ACCEPTED makes the stage TODO for ARP4, since no worker can accept a structure. The asks stage waits until the asks ledger holds every ask the UNRESOLVED elements name.

## Asks: one decision at a time (1.1)

Each open setting of a 1.1 input may carry `cause` (OWNER_DECISION, WAITS_FOR, EXTERNAL_DATA, DESIGNER_TASK, BUILD_NOTE) and, for the first three, `ask` (the decision it belongs to). `aws-design flow init` adds the asks stage after the gates (`--no-asks` leaves it out). The ledger is the one way the design asks people: it also carries, as asks without settings, the system overview's open questions and missing quality targets and AWS defaults that need confirming, whose answers the designer writes into the overview or the input. `aws-design asks start --workspace WS` lists the open settings per ask and those nobody classified; an agent drafts `asks/ledger.json` (contract `ask-ledger`: per decision the question, audience, background citing cells with a `quote` they hold, options with impact and the settings each decides, a free value with its kind and limits, due, `waits_for`, `depends_on`, `only_if` follow-ups, `critical`, `requirement_conflict`). `aws-design asks check` refuses unclassified settings, asks without a way to answer, options that leave an ask's settings open or set others, quotes the cited cells do not hold, unknown or circular dependencies, mismatched follow-ups and any option whose effects make the input invalid. `aws-design asks review --decision accepted|rejected --actor A --reason R` records an independent review (not the author). `aws-design asks status` derives each decision's state from the files; `sheet` makes the next batch in `asks/batches/NNN` (overdue, go-live, requirement conflicts, most waiting on it, earliest due; at most `--per-sheet` per audience; shared decisions to `agenda.md`) with `asks/board.md` and `asks/tasks.md`. `record --workbook ANSWERED.xlsx | --ask ID --answer a|保留|値 [--value V] --by NAME [--on DATE] [--dry-run]` checks each answer (option, typed value in its limits, a reason for 保留, a person's name, a valid input with every unapplied answer) and says what it sets; `ready --ask ID --by NAME` records that what an ask waits for happened or that a held ask may be asked again. `apply` writes every answered decision into `input/<name>-asks-NNN.json` with the record as source and points flow.json at it. `aws-design flow run all` performs `sheet` and `apply` itself.

## Organisation library

A library folder carries what one project learned to the next: `dictionary.json` (organisation-wide external-sheet dictionary) with `promotions.json`, `policy-packs/*.json` and `overview-templates/*.json`. `aws-design library promote --library LIB --dictionary PROJECT_DICT --promoter NAME [--entry ID ...]` adds approved project entries, merging labels of entries that mean the same mapping and keeping the previous dictionary; the promoter is a person the user names. `aws-design library dictionary --library LIB [--project PROJECT_DICT] --output MERGED` gives one dictionary for `aws-design external --dictionary`. `aws-design library list [--library LIB]` lists packs and templates; `aws-design policy-pack … --library LIB` and `aws-design system init --template NAME [--library LIB]` look in the library before the bundled ones. A template (bundled: `three-tier-web`) adds an actor/boundary/component/flow/target shape whose components, flows and targets are all UNDECIDED with no requirement links, so it claims nothing until a drafter or a person fills it. `aws-design flow init --library LIB` puts the library into the next-step commands.

## Organisation templates

`aws-design export --pack runs/NNN/review-pack.json --template ORG.xlsx --mapping MAPPING.json --output NEW.xlsx` writes a generation into the organisation's own workbook. A `table` block appends one row per review-pack row (optionally only some resource types) under a header row; a `form` block copies a template sheet once per resource and writes properties (`Property` or `Property#field`) into fixed cells. Fields: `resource_id`, `resource_type`, `property`, `value`, `state`, `tier`, `documents`, `evidence_at`, `evidence`, `reasons`, `priority`, `item_id`. ## Policy packs

`aws-design policy-pack list|show|apply` adds a reusable set of project policies to a copy of the input. `apply INPUT --pack aws-security-baseline [--environment ENV ...] --adopted-by NAME --output NEW_INPUT` turns each rule into an ordinary `project_policies` declaration for every resource of its type, with the pack (ID, version, hash) as source and requirement. Declarations are CONFIRMED only with the adopter the user names; without `--adopted-by` they are UNCONFIRMED and every result needs review. A project declaration for the same resource and path wins (reported as skipped); applying the same pack twice is refused. Generate from the new file. `aws-security-baseline` holds 19 value rules aligned with part of AWS Foundational Security Best Practices (S3 public access block and default encryption, CloudFront viewer HTTPS and OAC signing, OpenSearch encryption and HTTPS, CloudTrail log validation and multi-region, RDS encryption and no public access, EBS encryption, DynamoDB PITR, ElastiCache encryption). It is a candidate standard, not proof of compliance.

## Review pack

Every generation also writes `review-pack.md`, `review-pack.json` and `review-pack.xlsx`. Each value gets a provenance tier from recorded facts only: TRANSCRIBED (a dictionary-approved trace row whose `conversion` is AS_WRITTEN), CONVERTED (dictionary-approved with a conversion), DECISION (expanded from a basic-design decision), CITED (generated with `--source-set` and found by the grounding check in the cells it cites; which property it went to is still read by a person), ASSUMED (`mode: DEFAULT`) and INTERPRETED (everything else, including every value of an input without a trace). P1 rows come in the order of who settles them, with the first reason naming it: 人の判断 (cause OWNER_DECISION, WAITS_FOR or EXTERNAL_DATA, with the ask), other gaps and findings, 設計者の宿題 (DESIGNER_TASK), 構築時の注意 (BUILD_NOTE); P2 lists interpretations before CITED values. Priorities: P1 needs a decision (missing or undecided inputs with the reason, defaults, values without a source, AWS FAIL/ERROR, project-policy FAIL/NEEDS_REVIEW, STALE_VALUE_IN_DESIGN, CFN differences, earlier NG, change after OK), P2 interpretation to confirm, P3 sample (converted values; the Markdown shows up to 10), P4 no check needed (transcribed or not applicable). Each row carries where the value was read and what the original says (the trace's `source_pointer` with label and cell text, else the first source locator and the rationale). The reviewer writes OK/NG in the workbook; `aws-design review-pack record --workbook review-pack.xlsx --reviewer NAME [--previous OLD] --output DECISIONS` binds each verdict to the row fingerprint, with a reviewer the user names. Pass `--review-decisions DECISIONS` to the next generation: unchanged OK rows are counted as DONE, changed OK rows and NG rows return as P1. Priorities order review work; they are not approval. Each generation also writes `review-pack.html`, an offline page that shows each value beside its original, filters by priority and takes OK/NG with a comment (J/K to move, O/N to mark); it exports `review-decisions.json` in the `record` form once the reviewer's name is entered. `aws-design review-pack import --file review-decisions.json --pack review-pack.json [--previous OLD] --output DECISIONS` refuses rows the pack does not have, changed fingerprints, other verdicts and a missing reviewer name.

To measure the pack against what people actually found, run `aws-design review-pack recall --findings FINDINGS --pack review-pack.json`. FINDINGS is JSON, CSV or XLSX with `id`, `resource_id` (or `resource_type`), `property` and `note`. The report gives `recall_p1`, `recall_p1_p2`, the P1/P2 `workload`, findings not in the pack and findings placed below P2. Matching is by resource and property only.

## Collection matrix

Every generation also writes `collection-matrix.json` and `collection-matrix.md`: one row per design setting or required-input obligation, in four states for people (確定 CONFIRMED, 要確認 REVIEW, 未記載 MISSING, 対象外 NOT_APPLICABLE), with the documents its sources name. A value realizing a declared decision (`decision_ids`) takes the decision's sources (`source_level: DECISION`) and a reference declared as a REFERENCE connection counts as `CONNECTION`. Flags mark CONFIRMED values without any basis (NO_SOURCE) or with only a resource-level source (RESOURCE_SOURCE_ONLY), and, with `--source-set`, values backed only by REFERENCE documents (REFERENCE_ONLY) or by no document of the set (NOT_IN_SOURCE_SET). The Markdown lists only rows to review; `summary.json.collection` holds the counts. The matrix shows where facts came from, not whether they were read correctly.

## Source set for ARP4 documents

Each scanned document also carries `signals.kind` (MINUTES, REQUIREMENTS, ARCHITECTURE, OPERATIONS, TEST, PROJECT, APPLICATION, DESIGN, from the first of its role cell, title, file name and folders that names one, with `kind_hint`), `signals.aws_services` (distinct AWS services its cells and drawing texts name) and `signals.infra_cells` (cells with an infrastructure word), and `relevance`: PRIMARY when the kind is MINUTES, REQUIREMENTS, ARCHITECTURE or OPERATIONS, an AWS service is named or three cells hold infrastructure words, else PERIPHERAL. Relevance is advice for reading, not a status; `show` prints it in the 関連度 column.

ARP4 parses every original below its sources folder, so older drafts, copies and archived versions sit beside the current documents. `aws-design sources` records which of them a design may cite.

1. `aws-design sources scan --arp-root ROOT --output PROPOSAL` groups documents into version families by the document's own ID cell (文書ID, 文書番号, Document ID …), else by file name without version, date, status and copy marks. It orders a family by the version next to a 版/版数/Version label or the single version in the first title cells, else by the file name. The newest distinct version is proposed CURRENT and older ones SUPERSEDED; byte-identical copies are EXCLUDED as DUPLICATE_OF. Families without a comparable version, and documents in archive folders (old, 旧, archive, versions/0.1 …) without a newer version elsewhere, stay UNDECIDED. A CURRENT candidate whose folder, role cell (位置付け, 種別, 文書区分 …) or title holds 参考, 提案, 見積, 受注前, 他社, proposal, reference, estimate, RFP … stays UNDECIDED as POSSIBLY_REFERENCE, with the cells in `signals.reference`: versions say which copy is newest, not whether a document is a design basis.
2. `aws-design sources show --source-set PROPOSAL` prints a table for the person who approves it, with each document's title and role cell and the cell or file name each version came from.
3. `aws-design sources approve --arp-root ROOT --proposal PROPOSAL --approver NAME [--set DOCUMENT_ID=STATUS ...] --output SET` accepts only a proposal identical to a fresh scan, refuses UNDECIDED documents, and refuses CURRENT or REFERENCE documents whose original changed or was removed after import (SOURCE_CHANGED, SOURCE_MISSING) or that have a re-import waiting (REIMPORT_PENDING). Statuses are CURRENT, SUPERSEDED, REFERENCE and EXCLUDED. The approver is a person the user names, never the agent.
4. `aws-design sources check --arp-root ROOT --source-set SET [--design INPUT]` compares the set with ARP4 now: DOCUMENT_CHANGED, DOCUMENT_REMOVED, UNLISTED_DOCUMENT (a new document may be a newer version) and the original-file issues above are errors for CURRENT and REFERENCE documents. With a 1.1 input, a source whose `locator` is `DOCUMENT_ID` or `DOCUMENT_ID#place` must not name a SUPERSEDED or EXCLUDED document (CITES_SUPERSEDED, CITES_EXCLUDED, with the newer document); REFERENCE and locators outside the set are warnings. `citations` counts the design objects citing each source and `current_not_cited` lists CURRENT documents the design never cites. Exit 0 is PASS, 2 is FAIL or an input error.
5. `aws-design external … --source-set SET` refuses a sheet that is not CURRENT or differs from the approved hashes.
6. `aws-design sources diff --arp-root ROOT --source-set SET [--markdown]` compares each SUPERSEDED document with its newer one: removed and added cells, removed and added design values (CIDR, IP, ARN, instance type, quantities with units), and values that no CURRENT or REFERENCE document holds any more. `check --design` warns STALE_VALUE_IN_DESIGN when a setting value still contains such a CIDR, IP, ARN or instance type.
7. `aws-design document INPUT --environment ENV --output FRESH_DIR --source-set SET --arp-root ROOT` runs the same check before generating. A FAIL prints `generation_status: SOURCE_SET_FAILED` with the error codes and writes nothing (exit 2); a PASS writes `source-set-check.json` and adds `source_set_status`, `source_set_warnings`, `source_set_approver` and `current_not_cited` to `summary.json`.

PASS means the cited documents are the approved current versions. It does not show that every needed fact was collected from them.

## Required-input checklist (1.0 and 1.1 inputs)

Document generation now also writes `checklist.json`, embeds it in `design.json`, and adds required-input and evidence sheets to the index workbook. Generation can succeed with missing or undecided inputs. Read `summary.json.input_completeness` separately from `GENERATED` and `NOT_EVALUATED`.

Input 1.1 generation also writes `optional-inputs.json` and the index sheet 未記載の任意項目: writable pinned-schema properties the environment's design does not set, at the top level and inside the objects it writes, with the schema description, schema default and notes (replacement on change, conditionally required). Properties the checklist requires, read-only, deprecated and those under unwritten or undecided parents are left out; alternatives are listed side by side. It is a reference list for people, not a finding: it adds no review-pack row and does not say a property should be set. `summary.json.optional_inputs` gives the counts.

The checklist reuses pinned CFN required constraints and directly applicable registered cfn-lint error JSON schemas. Necessity, three-valued condition results, input state, value resolution and verdict remain separate. Read-only outputs are excluded. One-of alternatives are not all made mandatory. Unknown conditions, unresolved references, empty values and unsupported preprocessing require review. `OMITTED` explicitly records omission; an input's NOT_APPLICABLE declaration cannot waive an AWS-required field. CFN values and defaults never fill absent design inputs.

Optional `required_inputs` declarations bind a requirement ID, resource ID, `/properties/...` pointer, source IDs, environments and optional JSON Schema `when` predicate. Explicit `confirmation: CONFIRMED` plus sources are needed for a firm project verdict. Sources missing or unconfirmed interpretations remain UNKNOWN/review. `allow_documented_default` only permits a project requirement to accept an explicit DEFAULT with direct top-level pinned-schema default metadata; it cannot exempt AWS-required obligations. CLI `--schema input --schema-version 1.1` prints the full contract.

Counters describe obligation rows and unique input paths, not all catalog properties or complete AWS coverage. General value correctness, conditions missing from schemas, Python-only/warning rules, project expected-value policies and deployment are outside this checklist. Project values use the separate policy layer below.

### Optional local AWS evaluation bridge

Add `--evaluate` to `aws-design document` to run the existing Checker and cfn-lint on the selected environment's effective design settings, for input 1.0 or 1.1. CFN remains optional and is used only for comparison: it never supplies missing design values. Invalid equal Runtime/TLS values can therefore be MATCH while AWS evaluation reports a finding. No project expected-value or live AWS checks are added.

Generation, comparison, required-input completeness, evaluator execution and AWS findings are separate axes. `evaluation.json`, normalized `design.json` and the index workbook's AWS評価 / AWS未検査 / AWS評価根拠 sheets retain results, unknowns, IDs, input pointers and source links. Evaluation is opt-in; existing calls remain NOT_EVALUATED. CLI returns 3 on evaluator failure or unsupported-region skip, 2 on structure/output errors, and 0 for completed generation/evaluation even when findings exist. Check `aws_assessment` and severities; there is no overall PASS.

Undecided/default/expression/secret values are unresolved, and so are external references unless bound as below. Internal references preserve declared targets but infer neither physical values nor Ref/GetAtt attributes. Synthetic lint templates are isolated per resource, marked non-deployable, and record placeholder mappings without defaults. Stack/account context, business requirements, application behavior, real permissions, performance and deployment remain outside scope. Conditional findings affected by unknown context are retained for review. Never reuse an existing output directory.

### Local values for external references

`--external-bindings FILE` supplies values the designer knows for EXTERNAL_REF settings (an existing VPC ID, a KMS key ARN). Format: `{"binding_version": "1.0", "environment": "prod", "bindings": [{"ref": "kms-key-alias/portal", "value": "alias/portal", "source": "key inventory 2026-10"}]}`; `environment` is optional and must match. Each use of a bound ref is checked against the regional pinned schema's JSON type: BOUND values become evaluation inputs for `--evaluate` (coverage `EXTERNAL_VALUE_BOUND`), SHAPE_MISMATCH and UNBOUND stay unknown (`BRIDGE_UNKNOWN_VALUE`, reason `EXTERNAL_REF_BINDING_SHAPE_MISMATCH` for a mismatch). Every ARN in a bound value must also carry the resource's region and partition (global ARNs such as S3 and IAM have none); CloudFront viewer ACM certificates and WebACLs must be in us-east-1. Otherwise the use is REGION_MISMATCH with `expected_region` and the ARN regions found, and stays unknown (`EXTERNAL_REF_BINDING_REGION_MISMATCH`). Backup copy destinations, KMS replica primary keys and RDS cross-region replica sources point elsewhere by design: they stay BOUND and record `cross_region`. With `--evaluate`, decided literal ARNs in the design get the same region test as rule `DOCUMENT_ARN_REGION` (stage `declared_regions`): FAIL (ERROR) for a CloudFront certificate or WebACL outside us-east-1, NEEDS_REVIEW (WARNING) for any other ARN whose region or partition differs from its resource, PASS for the fixed-region and by-design properties; matching ARNs add no row. The design input and workbook keep the reference. `review-report.json.external_bindings` and `summary.json.external_bindings` give the counts and unused refs. Nothing is fetched from AWS: existence, ownership and current state stay unverified. Duplicate refs, secret-like values, a ref also used by SECRET_REF or a SECRET setting, sensitive properties and a different environment stop with `BINDING_ERROR` (exit 2); the message names codes and refs, never values.

### Explicit project policies

Input 1.0/1.1 may declare `project_policies`: each has a stable id, requirement_id, resource_id, writable property JSON Pointer `path`, `operator` (EQUALS or IN), scalar `values`, explicit environments, sources, rationale, and confirmation (default UNCONFIRMED). Optional `when` is a conjunction of up to 16 predicates of the same form on the same resource. Rules are human mappings; no prose or arbitrary expression/code is executed. Array `*` selects every member; empty selections and unknown values require review. Numbers, booleans, empty strings and null are distinct.

Declared policies run during document generation. `--evaluate` additionally runs the independent AWS layer; optional CFN only supplies comparison data. Missing/default/Ref/GetAtt/internal/external/secret values are never filled or resolved for policy checks. PROJECT_POLICY failure says this project's choice was violated, not that AWS universally prohibits the value. Q02-style BlockPublicAcls=false is not proof of public exposure.

`policy_exceptions` require an id, one policy_id, concrete paths within its selector, explicit environments, reason, sources and confirmation. Confirmed exceptions turn known mismatches into EXEMPTED, never PASS; unknowns cannot be waived into success. Invalid syntax, references or exception scope produce POLICY_CONFIGURATION_ERROR (exit 2); evaluator failure produces FAILED/ERROR (exit 3). No credential values or exception text are logged on errors.

Inspect `project_policy_status`, `project_policy_assessment`, `project-policy.json`, and workbook 案件方針 / 案件方針根拠 / 案件要件範囲. IDs, declaration/value pointers, conditions, sources and exceptions are retained. Unregistered requirements remain listed; COMPLIANT_WITHIN_DECLARED_SCOPE is never whole-requirement or whole-design approval. APP business controls, real AWS validation and prose extraction remain outside scope. A design can complete generation and AWS evaluation while recording NONCOMPLIANT in the separate project policy assessment.

## Immutable official schema cache

`schemas/schema-lock.json` fixes the source URL, region, review time, tool version, ZIP SHA-256, previous type fingerprints and expected generated catalog/rule hashes. Bootstrap records the actual retrieval timestamp in `schemas/.cache/<hash>/schemas/manifest.json`, with its tool version and source. The sibling `catalog.json`, `reconciliation.json`, `rules/` and `generation.json` record the locally generated results. No ZIP members are extracted to filesystem paths.

Use `aws-design bootstrap --check` to verify an existing cache offline. Re-running `aws-design bootstrap` verifies and reuses it without network access or changes. After a failed first setup, retry bootstrap from the already installed environment; rerunning the installer itself intentionally refuses an existing `.venv`. Partial downloads and failed generation directories remain in `schemas/.downloads/`. Existing or corrupt cache directories are never silently replaced. Preserve a damaged cache elsewhere or install a fresh skill copy before recovering.

If AWS changes the public URL contents, acquisition stops with a hash mismatch. A maintainer must review the new schema, regenerate the lock/catalog/rule expectations and rerun regressions; users should install that reviewed release in a new directory. Never remove the pin. Old generations and unrelated files are preserved. Base rule edits also invalidate the reviewed lock instead of silently using an inconsistent catalog. The released `aws-design-schemas` default destination cannot overwrite this contract.

Installed local generation, required-input/policy checks and AWS static evaluation operate offline. Optional LLM extraction and new source-document retrieval do not. Missing or invalid schemas cause a setup/configuration failure, never a PASS. The live host apps themselves are not covered by Python CLI tests.

The official URL is mutable and is not a versioned archive service. After it changes, the same locked ZIP may no longer be obtainable for a fresh install. Preserve a verified cache for repeatable offline runs, or use a newly reviewed release; do not weaken hash validation.
